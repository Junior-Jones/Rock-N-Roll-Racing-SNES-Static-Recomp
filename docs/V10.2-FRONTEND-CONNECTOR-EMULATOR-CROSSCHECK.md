# V10.2 frontend connector cross-check

## Scope

The Windows connector was checked against three mature, independently maintained SNES emulators. The local reference checkouts are pinned under `research/mature-emulators`:

- Mesen2 `b9fa69ddc6d0a331fb103fdb5eef6904305703c2`
- Snes9x `a0420aef6a5df627c1ddd00495f3eb32b6ef8aa3`
- bsnes `7d5aa1e656b9171524d01b1b22917197d8121cb4`

This is a boundary-contract review. It does not copy emulator code into the recompilation and it does not use an emulator as production authority for undiscovered S-CPU execution.

## Findings and production decisions

| Boundary | Mature-emulator behavior | V10.2 connector decision |
|---|---|---|
| Frame completion | Mesen publishes at its PPU end-frame path; bsnes returns to the UI only at a completed frame event; Snes9x's main loop is one emulated frame. | `rnr_recomp_advance` runs until `frame_sequence` changes and publishes only that completed frame. It never exposes a partially rendered framebuffer. |
| Controller polling | All three use the SNES serial order B, Y, Select, Start, Up, Down, Left, Right, A, X, L, R. Mesen and bsnes neutralize impossible opposite D-pad pairs. | The launcher latch uses the same bit contract. Up+Down and Left+Right are neutralized only at the connector boundary, leaving the frontend's raw key state truthful. Port 2 is explicitly zeroed for this one-player route. |
| Pixel ownership | The emulator core owns SNES color data and the host consumes a completed output frame. | The connector owns a stable 256x224 host buffer and converts SNES BGR555 into packed BGRA only after frame completion. Screenshots consume this same stable buffer. |
| Native height | SNES overscan is controlled by SETINI. | Static source evidence shows Rock n' Roll Racing writes zero to SETINI at its identified sites, so 224 active lines are correct for this target. A future game that enables overscan must expose a dynamic 239-line contract instead of silently cropping it. |
| Audio format | Snes9x documents interleaved signed 16-bit stereo; Mesen flushes SPC frames into its sound mixer; bsnes emits one stereo audio frame at a time. | The APU sink appends signed 16-bit interleaved stereo to a connector-owned queue. The frontend drains that queue into SDL; the core never owns an SDL buffer. |
| Audio rate | Mature implementations use the SNES DSP rate near 32040 Hz and correct small host-device drift in the output layer. | The static core remains at its hardware-derived rate. The frontend resampler/queue applies only bounded host pacing correction; it never changes the S-CPU or SPC master clock to chase a device buffer. |
| ROM lifetime | Emulator frontends keep cartridge data alive independently of a file dialog's temporary buffer. | The connector verifies the exact 1 MiB USA ROM and SHA-256, then keeps a private ROM copy for the machine lifetime. |
| Reset | Emulator frontends separate machine reset from application/resource lifetime. | Launcher Reset performs the product's defined cold restart by shutting down and powering on the machine while retaining connector-owned host buffers. |
| Failure handling | Production emulators surface fatal core failures rather than continuing with corrupt state. | Any static stop fails closed and reports frame, clock, PC, opcode, stop kind, detail, and recent execution history. |

## Result

The connector now follows the common mature-emulator model: sample input at the frame boundary, execute to one completed frame, publish a stable image, queue all native audio generated by that interval, and let the host presentation layer pace display and device delivery. The cross-check found and corrected two boundary details: opposing-direction neutralization and using `frame_sequence` as the public completed-frame number.

The natural route and long-duration gates remain the final target-specific validation. They must prove that these correct generic boundaries also remain stable through real Rock n' Roll Racing menus and gameplay.
